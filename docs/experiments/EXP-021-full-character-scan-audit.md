Following characters were in multiple cases recognized correctly, arguing against *permanent* navigation derailment. This is an independent *false accepted OCR talent*, not caused by passive talents as such. Require row-specific trusted OCR / reasonable sanity checks, and flag ambiguous talent reads rather than quietly exporting them.

Prior Oct 15 GOOD reports C5. Her C5 node failed all OCR retries -> false negative. - A composite review of **all 62 screenshots from first rejected constellation nodes** found those two are the clear cases with visible `Activated` text. The others show no text at the targeted location (or another unrelated constellation title), consistent with locked state. Therefore do **not** conclude the entire reverse traversal is wrong.
- Relative to the Oct 15 GOOD, other three differences: `Wanderer` C0→C1, `Diluc` C1→C2, `Freminet` C1→C2. The currently captured respective C1/C2 nodes visibly say `Activated`. These changes **may be genuine character progression** (wishes). Do not overwrite without the user's confirmation.
- Actual detector `ReadConstellationActivated` uses 3 Tesseract OCR attempts on gamma (0.2) + invert + grayscale, and returns true only if detected text contains exact `activated`. Failure to read highly bright `Activated` causes premature stopping in the C6-first traversal. Proposed EXP-022 fix should be *targeted preprocessing/view fallback* and recorded screen-vs-export regression tests, not unconditional trust in the first screenshot. Do not change controller move logic just because a value differs.
